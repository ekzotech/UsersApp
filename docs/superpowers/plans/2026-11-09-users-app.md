# UsersApp — управление пользователями (студенты и преподаватели) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpower-subagent-driven-development (recommended) or superpower-executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Every task is delivered as exactly ONE git commit; the commit is reviewed by another subagent before the next task starts; a phase is merged into `main` only after all its tasks are reviewed and merged into the phase branch.

**Goal:** SSR-приложение на Java/Spring Boot для управления пользователями: вход, создание студентов и преподавателей, активация/деактивация, кураторство (у преподавателя роль «Куратор»), назначение студентов на предметы к разным преподавателям; PostgreSQL + Flyway, seed через Faker (сотни студентов) при первом запуске; весь код разработан через TDD (Red → Green); unit/component-тесты с моками (Mockito) и E2E-тесты (Playwright); Docker Compose поднимает БД и приложение.

**Architecture:** Монолит Spring Boot 3.5 (Java 21) + Spring MVC + Thymeleaf (server-side rendering) + Spring Security (form login, сессия) + Spring Data JPA + Flyway (DDL и SQL-справочники в V-миграциях; Faker-seed — идемпотентный `ApplicationRunner` в профиле `seed`, включён по умолчанию). Слои: `domain` (сущности и доменные правила) → `service` (транзакции, валидация бизнес-правил) → `web` (контроллеры + формы + Thymeleaf-шаблоны). Тесты: JUnit 5 + Mockito (unit/component, моки репозиториев — по требованию «для тестов компонентов используй mock»), `@DataJpaTest` на реальном PostgreSQL через Testcontainers (миграции + инварианты БД), `@SpringBootTest` + `MockMvc` для security/CSRF, Playwright (`@playwright/test`) против стека из docker compose.

**Tech Stack:** Java 21, Maven 3.9, Spring Boot 3.5.x, Spring Security, Spring Data JPA, Flyway, PostgreSQL 17, Lombok, datafaker, Thymeleaf, Testcontainers 1.20.x (postgresql), Mockito, Playwright 1.56 (Chromium), Docker Compose.

**Spec:** этого отдельного документа нет; исполняемые требования — этот план + исходный запрос пользователя (см. «Цель», «Global Constraints», «Функциональные требования»).

## Функциональные требования (контракт)

1. **Вход**: страница `GET /login` (логин, пароль), вход по username; после входа только аутентифицированные пользователи имеют доступ ко всему (кроме `/login`, `/css/**`, `/error`). Неверный пароль → редирект на `/login?error`. Выход `POST /logout` → `/login?logout`. Пользователь без `ROLE_ADMIN` получает 403 на `/admin/**`.
2. **Каталог пользователей** `GET /users`: список всех студентов и преподавателей (имя, email, тип, статус, куратор/кол-во куратее), поиск по ФИО/email через `?q=`.
3. **Создание студента** `GET|POST /students/new`: поля ФИО (`fullName`, 2–100 символов), email (обязателен, формат email, уникален без учёта регистра), группа (`groupName`, 2–20). Новый студент активен.
4. **Создание преподавателя** `GET|POST /teachers/new`: ФИО, email (те же правила), признак «роль Куратор» (`curator`, чекбокс), поля «Логин» (`username`) и «Пароль» (`password`) — создают учётную запись администратора; `username` уникален, пароль ≥ 8 символов, хранится BCrypt.
5. **Активация/деактивация** `POST /students/{id}/activate|deactivate`, `POST /teachers/{id}/activate|deactivate`: студент → «Отчислен», преподаватель → «Уволен». RBAC: `ADMIN` на `/students/**`, `/teachers/**`, `/admin/**`; `TEACHER` (преподаватель-куратор) на `/curator/**`. Куратор и преподаватель-предметник — независимые атрибуты.
6. **Кураторство**: у студента ровно один куратор или ни одного (`student.curator_id`); назначать можно только преподавателя с ролью «Куратор»; нельзя назначить уволенного/отчисленного. `POST /curator/students/{id}/curator` (поле `curatorId`) переназначает или снимает куратора; доступно только куратору — **только своим** студентам (чужой → 403).
7. **Предметы**: ровно 12, seed через SQL-миграцию: математика, физика, химия, русский язык, английский язык, русская литература, английская литература, история, философия, психология, социология, экономика. Карточка преподавателя `GET /teachers/{id}` показывает его предметы и назначенных студентов.
8. **Назначение на предмет** `POST /teachers/{id}/courses/{courseId}/students` (параметр `studentId`): один студент → разные преподаватели по разным предметам; мягкий лимит `MAX_STUDENTS_PER_COURSE_PER_TEACHER = 60` (превышение → ошибка формы, без исключения 500).
9. Seed (профиль `seed`, включён по умолчанию, идемпотентен — при вторичном запуске ничего не дублирует): 12 предметов из миграции; ~300 студентов, ~12 преподавателей (~6 кураторов) через Faker с фиксированным `seed=42`; у большинства студентов есть ровно один куратор; каждое назначение предмета — преподаватель с предметом в компетенциях; учётная запись админа `admin` / пароль из `APP_ADMIN_PASSWORD` (по умолчанию `admin12345`), одна учётка куратора для демо.
10. **UI**: минималистичный, mobile first (одна колонка, ≤ 720px центрированная колонка на десктопе), CSRF-токен в каждой форме POST, сообщения flash после действий.
11. **Docker Compose**: `db` (postgres:17-alpine, volume, healthcheck) + `app` (multi-stage build, `depends_on: db (healthy)`, порт хоста 8081). Первый запуск с пустым volume → Flyway создаёт структуру, seed наполняет БД.

## Review Focus

1. CSRF: форма без `_csrf` после логина → 403, а не 500; все формы POST в шаблонах содержат `<input type="hidden" name="_csrf" ...>`.
2. Дубликаты: повторная отправка формы/повторный запуск seed не создаёт вторых пользователей (email unique + идемпотентный seed).
3. Невалидные назначения (уволенный преподаватель, отчисленный студент, не-куратор в `curatorId`) → ошибка, не 500.
4. Куратор не может менять чужих студентов (403) и не может обращаться к `/students/**` (403).
5. Битые входы: `id` = `abc`/несуществующий → 404 (не 500); пустые поля формы → перерисовка формы с ошибками и сохранением введённого.
